## At a glance

A **WORK ITEM** with an **IDEMPOTENCY KEY**.

Two **ATTEMPT** lanes. Each starts with **CHECK DEDUP STORE**.

If a **RECEIPT FOUND**, the same result is returned and the work is complete.

If **NO RECEIPT FOUND**, the work is processed. In **ATTEMPT 1**, the work times out and loops back. In **ATTEMPT 2**, the work fails permanently, hits the **RETRY BUDGET**, and when the budget is exhausted, goes to **POISON / DEAD LETTER**.

And on the right, a green shield: **NO INFINITE LOOP**.

A retry is a second attempt at one intention, not a second intention. The idempotency key is how the system tells the difference.

## What the diagram teaches

### 1. A retry is a second attempt, not a second intention

The diagram shows one **WORK ITEM** on the left and two **ATTEMPT** lanes on the right. The work item is the same. The attempts are different.

That is the mental model. The user asked for one thing. The transport timed out. The transport retried. The system is still answering the same request.

If the retry creates a new intention, it is not a retry — it is a new request. The diagram keeps this clear by having the same work item feed both attempts. The **IDEMPOTENCY KEY** on the work item is the identity of the intention, not of the attempt.

### 2. The idempotency key must be generated before the first side effect

Look at the position of the **IDEMPOTENCY KEY** label. It is on the **WORK ITEM**, before any attempt begins.

That timing is the rule. The key must exist before the first attempt touches the outside world. If you generate it after a partial success, you cannot prove that the first and second attempts are the same intention.

The key is not the message ID. Message IDs are generated by the transport and may change on redelivery. The idempotency key is a business identity: order-42, refund-xyz-2026-03-15. It names the thing the user wanted to happen, not the envelope it travelled in.

### 3. CHECK DEDUP STORE is the first step of every attempt

Both **ATTEMPT 1** and **ATTEMPT 2** start at the same box: **CHECK DEDUP STORE**.

That means the dedup check is not a special case. It is the normal entry point. Every attempt, on arrival, asks: *has this intention already produced a durable result?*

If the answer is yes, the attempt does not process the work. It returns the stored result. If the answer is no, it continues.

This is why the dedup store must be checked before the side effect. Once the side effect has started, the question becomes harder and the answer more expensive.

### 4. RECEIPT FOUND returns the same result, and that is the whole point

The **teal** path in both attempts is the same: **RECEIPT FOUND → RETURN SAME RESULT → ACKNOWLEDGEMENT → COMPLETE**.

The result does not have to be recomputed. The receipt does not have to be re-fetched. The work does not have to be redone. The dedup store holds the outcome of the first successful attempt, and any later attempt returns it.

This is what makes retries safe. It is not that the side effect is harmless to repeat. It is that the side effect is not repeated. The second attempt sees that the first one already happened and answers with the same outcome.

### 5. PROCESS WORK happens only when no receipt exists, and timeout is not a result

The **red** path drops from **NO RECEIPT FOUND** to **PROCESS WORK**. This is the side-effect path, and it is the only place where the outside world is touched.

In **ATTEMPT 1**, **PROCESS WORK** leads to **TIMEOUT**. The timeout is a transport failure. It is not a business result. No receipt has been written, so the work item loops back for redelivery.

The **NO ACKNOWLEDGEMENT** arrow looping back to the work item is the queue saying: *I never heard you finish, so I am exposing the work again.*

That is the correct behaviour. The work is not complete, and the queue should not delete it.

### 6. Permanent failure and retry budget stop the loop

In **ATTEMPT 2**, **PROCESS WORK** leads to **PERMANENT FAILURE**. A permanent failure is not a timeout. It is a result: the work cannot be done as requested. The data is bad, the rule is violated, the external dependency refuses.

The attempt then reaches the **RETRY BUDGET**. The diagram draws a dashed green arrow labelled **BUDGET REMAINING** feeding back from the budget to **PROCESS WORK**. That means if the budget is not exhausted, the work can be retried again.

But if the budget is exhausted, the arrow turns red and the work goes to **POISON / DEAD LETTER**. A skull on the box. The work is quarantined so it cannot keep consuming attempts.

The **NO INFINITE LOOP** shield on the right is the diagram's guarantee. A bounded retry budget plus a poison-work lane is how a system retries safely without becoming a denial-of-service attack against itself.

### 7. The previous pattern is what redelivers this one; this pattern is what makes redelivery safe

The diagram to the left of this one in the course is the queue with a lease. A worker crashes, the lease expires, and the same item is redelivered to another worker.

![A PRODUCER sends work to a DURABLE QUEUE, which leases it to WORKER A through a visibility window. WORKER A processes the work, writes a RECEIPT, ACKs the queue, and reaches COMPLETE. A coral dashed path shows WORKER A crashing, the LEASE EXPIRING, and the SAME ITEM being redelivered to WORKER B.](../diagrams/129-queue-lease-ack-visibility.png)

That redelivery is a retry in the transport layer. Without an idempotency key, redelivery turns one side effect into two. With it, the second worker checks the dedup store, sees the first worker's receipt, returns the same result, and the queue is correctly acknowledged.

The two diagrams are a pair. The first says the queue must be able to redeliver. The second says the worker must be able to handle the same item twice without duplicating the effect.

## Case study — Hartwell Logistics, the pallets that shipped twice

Hartwell handles shipping for about 260 mid-sized retailers. Every order produces a shipping label, a carrier pickup, and a tracking number. Their label-printing worker ran from a queue with a visibility window.

### What they had

A worker that received an order, printed a shipping label, called the carrier API, stored the tracking number, and acknowledged the queue.

There was no idempotency key. The worker used the order ID as its queue item key, but the carrier API generated a new tracking number on every call.

### The four days

A carrier integration had intermittent timeouts. The worker would call the API, the call would hang, the visibility window would expire, and the queue would redeliver.

The redelivered worker had no record of the previous call. It called the API again. The carrier created a second shipment.

Over four days, this happened for 312 orders. The customer received two packages for each. Hartwell paid for 312 extra shipments, and the customer had to return the duplicates.

### What they tried first

They extended the visibility window from 30 seconds to two minutes. That reduced the timeout rate, because more carrier calls completed before the lease expired.

But the real problem was not the timeout. It was that a redelivered worker could not tell whether the carrier had already accepted the shipment.

A long visibility window only hides the problem. It does not solve it.

### The fix

**Idempotency key per order.** Generated when the order was enqueued, before the first carrier call.

**Dedup store.** One record per idempotency key, with four fields: **request fingerprint** (order contents, destination, weight), **carrier call attempt**, **carrier tracking number**, **status**.

The request fingerprint matters because the key must not be reused for a different order. If a customer changes the shipping address, the key changes.

**Check before call.** Every worker, on receiving an order, checks the dedup store. If the tracking number is already there, it returns it and ACKs. If an attempt is in flight with no result, the worker waits or extends the lease. If there is no record, it calls the carrier.

**Receipt before ACK.** The carrier's response is stored as a receipt before the queue is acknowledged. A crash between the carrier response and the ACK now leaves a receipt behind, so redelivery is safe.

**Retry budget and poison queue.** Carrier calls that fail with a 5xx are retried up to three times over ten minutes. Carrier calls that fail with a 4xx are sent to a poison queue after one attempt, because the request itself is wrong.

### Results

- **Duplicate shipments from queue redelivery:** 312 over four days → 0.
- **Extra carrier charges from duplicate labels:** £18,700 → 0.
- **Visibility window:** 30s → 2min, then back to 45s after the dedup store was added, because the lease no longer had to outlast the whole uncertainty window.
- **Poison queue size on launch:** 14 orders with bad addresses, caught immediately instead of retrying forever.
- **Mean time to ship an order:** unchanged.

### The line in their operations standard

*A redelivered message is not a new request. If the same idempotency key can produce a second side effect, the retry is not safe.*

## Composition

A left-to-right fan: one work item feeds two attempt lanes, with a poison-work exit and a loop-control shield.

**Left:** **WORK ITEM** — a white document on a blue platform, with a green badge below reading **IDEMPOTENCY KEY**.

**Two cyan arrows** fan right into **ATTEMPT 1** and **ATTEMPT 2** — blue platforms with rounded tops.

**Each attempt begins** at **CHECK DEDUP STORE** — a white card with a database and magnifier.

**Teal success path:** **RECEIPT FOUND** (teal text) → **RETURN SAME RESULT** (white card with a check) → **ACKNOWLEDGEMENT** (teal text) → **COMPLETE** (white card with a check). This path appears in both attempts.

**Red failure path (ATTEMPT 1):** **NO RECEIPT FOUND** (red text) → **PROCESS WORK** (white card with a gear) → **TIMEOUT** (white card with a red clock) → a **dashed red arrow labelled NO ACKNOWLEDGEMENT** looping back to the **WORK ITEM**.

**Red failure path (ATTEMPT 2):** **NO RECEIPT FOUND** → **PROCESS WORK** → **PERMANENT FAILURE** (white card with a red X) → **RETRY BUDGET** (white card with a gauge) → a **red arrow labelled BUDGET EXHAUSTED** → **POISON / DEAD LETTER** (red box with a skull).

**Feedback loops:** a **dashed green arrow labelled BUDGET REMAINING** loops from **RETRY BUDGET** back to **PROCESS WORK**, and a **dashed teal arrow labelled RECEIPT EXISTS** loops from the receipt-check point in ATTEMPT 1 back to **RETURN SAME RESULT**.

**Far right:** a **green shield** reading **NO INFINITE LOOP**.

## Element by element

**WORK ITEM** — one intention, not one message.
**IDEMPOTENCY KEY** — the identity of that intention, generated before the first side effect.

**ATTEMPT 1 / ATTEMPT 2** — separate tries at the same intention.
**CHECK DEDUP STORE** — the first step of every attempt.

**RECEIPT FOUND** — a previous attempt produced a durable result.
**RETURN SAME RESULT** — do not repeat the side effect; answer with what happened.
**ACKNOWLEDGEMENT → COMPLETE** — the queue and the workflow are both settled.

**NO RECEIPT FOUND** — the work must actually be attempted.
**PROCESS WORK** — the side effect itself.

**TIMEOUT** — a transient failure; no result, so the work loops back.
**NO ACKNOWLEDGEMENT** — the queue's way of saying the result never arrived.

**PERMANENT FAILURE** — the work cannot be done.
**RETRY BUDGET** — a bounded number of tries.
**BUDGET REMAINING** — the loop continues.
**BUDGET EXHAUSTED** — the loop stops.
**POISON / DEAD LETTER** — quarantine for unprocessable work.

**NO INFINITE LOOP** — the diagram's guarantee.

## Colour and flow semantics

- **Cyan arrows** carry the work item into both attempts — the same intention, different tries.
- **Teal** marks the success path: receipt found, same result returned, acknowledgement, complete. The same colour is used for the receipt-exists shortcut that avoids repeating work.
- **Red** marks the failure and retry path: no receipt, process work, timeout or permanent failure, retry budget.
- **Red dashed** carries **NO ACKNOWLEDGEMENT** back to the work item — a retry because the result never arrived.
- **Green dashed** carries **BUDGET REMAINING** back to process work — a retry because the budget allows it.
- **Red** on **BUDGET EXHAUSTED** and **POISON / DEAD LETTER** marks the termination of the loop.
- The **green shield** is the diagram's central claim: with a dedup store and a retry budget, retries do not become infinite loops.

## How to present it

**Start with the distinction between an attempt and an intention.** A user clicks submit once. The network times out and the client retries. Is that two orders or one? The answer depends on the idempotency key, not on the number of network calls.

**Point at the IDEMPOTENCY KEY on the work item, not on the attempts.** It is generated before the first side effect. Ask when their system creates it. If the answer is "after the request is received," that is too late.

**Trace the two attempts from the same work item.** Attempt 1 and Attempt 2 are not two different orders. They are two attempts at the same order. The dedup store is what makes them the same.

**Emphasise CHECK DEDUP STORE as the first step.** Every attempt asks the question first. If the receipt exists, the side effect does not happen. If it does not, the work proceeds.

**Make the teal path the happy path.** Receipt found, same result returned, complete. The second attempt is faster and cheaper than the first because it does not touch the outside world.

**Show the red path in Attempt 1.** Process, timeout, no acknowledgement, loop back. This is a redelivery from the queue. It is normal and safe as long as the dedup store is checked.

**Show the red path in Attempt 2.** Process, permanent failure, retry budget, budget exhausted, poison. This is the loop control. Ask what their system does when the same item has failed ten times. If the answer is "keep retrying forever," it is not a retry system; it is a denial-of-service system.

**Tell the Hartwell story.** 312 duplicate shipments over four days because the queue redelivered and the worker had no receipt. The carrier created a new tracking number every time. The fix: idempotency key, dedup store with carrier tracking number, receipt before ACK, retry budget, poison queue.

**Point at NO INFINITE LOOP and ask what bounds their retries.** A budget is not optional. Without it, a poison item will consume workers until someone notices.

**Close with the standard.** *A redelivered message is not a new request. If the same idempotency key can produce a second side effect, the retry is not safe.*

**Timing.** Twenty-five minutes. Thirty if you inspect one real retry path and asks whether a redelivery would produce the same result or a second one.

## Lab and checkpoint

**Lab:** Inspect one retry path in your system. Confirm the idempotency key is generated before the first side effect, the dedup store is checked at the start of every attempt, and a found receipt returns the same result. Add a retry budget and a poison queue for items that exhaust the budget.

**Checkpoint:** Why must the idempotency key be generated before the first side effect?

**Answer:** Because the key must identify the intention before any work is done. If it is generated after the first side effect, a redelivery or a retry before the key is stored can create a second side effect. The key is what makes two attempts the same request.

## Glossary

- **Attempt** — one execution of a work item.
- **Dedup store** — the durable store that records idempotency keys and receipts.
- **Idempotency key** — the identifier that makes retries safe.
- **Permanent failure** — an error that will not be fixed by retrying.
- **Poison work** — an item that repeatedly fails and must be quarantined.
- **Receipt** — the durable record that an attempt was completed.
- **Redelivery** — the queue sending the same work item again.
- **Retry budget** — the maximum number of attempts before treating an item as poison.
- **Same result** — the outcome of a retry when the work was already done.
- **Side effect** — an external change caused by the work.
- **Timeout** — a temporary failure that should be retried.
