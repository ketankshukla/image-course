Keep gate policy pure and testable, coordinate long-running runs durably, isolate evidence stores, and expose the same framework-neutral contracts as the TypeScript stack.

## Case study — Maya receives a plausible but obsolete refund policy answer

Maya receives a plausible answer citing an obsolete refund policy during a candidate rollout.

### The walkthrough

1. The business receipt links the artifact to a trace whose retrieval span names the stale document and index version without copying private content.
2. The freshness assertion fails, the stale-policy slice crosses its proposed guardrail, and the release gate pauses the candidate.
3. The interface preserves valid research, explains the failure, and offers current-evidence retry or human review while rollback restores a known-good bundle.
4. The incident creates owned actions, a stale-current dataset expansion, an alert exercise, and permanent stage and end-to-end regression cases.

### The result

One evidence chain explains the defect, protects Maya, controls release risk, verifies recovery, and makes recurrence harder.

### The danger

Buying one observability product and recording every prompt does not create AgentOps; without cases, stage contracts, budgets, release rules, ownership, and regression learning, it creates an expensive data lake of uncertainty.

### The takeaway

Connect user outcome to stage evidence, release decisions, recovery, and permanent learning.

## Composition

The ACME AGENT QUALITY LAB sits at the center of the diagram as a large control-room platform. Around it, twelve connected systems are arranged in a ring: TELEMETRY CONTRACT, TRACE EXPLORER, EVAL DATASET, SCORERS, STAGE QUALITY, LATENCY COST CAPACITY, RELEASE GATES, SHADOW CANARY, FLAGS ROLLBACK, ALERTS RUNBOOKS, INCIDENTS, and REGRESSION LEDGER. Cyan input arrows enter from the left from NEXT.JS, FASTAPI, MCP, A2A, RAG, TOOLS, QUEUES, and UI. A teal loop returns VERIFIED LEARNING to BUILD, while a coral STALE ANSWER is caught at RETRIEVAL and blocks RELEASE. The composition is a single control-room view: every major operating function orbits the central lab, inputs arrive from the real system, and two loops show success and failure.

## Element by element

- **ACME AGENT QUALITY LAB** — The **ACME AGENT QUALITY LAB** is the evidence and operating layer around the future agent product.
- **TELEMETRY CONTRACT** — The **TELEMETRY CONTRACT** is the agreement that defines signals, attributes, propagation, capture, and access.
- **TRACE EXPLORER** — The **TRACE EXPLORER** is the operator view for inspecting connected traces, spans, and events.
- **EVAL DATASET** — The **EVAL DATASET** is the versioned collection of cases used to judge system behavior.
- **SCORERS** — The **SCORERS** are the instruments that evaluate case evidence against a rubric or assertions.
- **STAGE QUALITY** — The **STAGE QUALITY** is the measurement of each agent stage—intent, routing, retrieval, tool, planning, and so on—separately.
- **LATENCY COST CAPACITY** — The **LATENCY COST CAPACITY** is the performance and economics view of the system: deadlines, cost, queues, and saturation.
- **RELEASE GATES** — The **RELEASE GATES** are the offline and production evidence rules that decide whether a candidate may promote.
- **SHADOW CANARY** — The **SHADOW CANARY** is the side-by-side and small-cohort release methods that compare versions with real workload.
- **FLAGS ROLLBACK** — The **FLAGS ROLLBACK** is the feature flags and emergency rollback controls that expose or revert a version bundle.
- **ALERTS RUNBOOKS** — The **ALERTS RUNBOOKS** are the actionable alerts and tested runbooks that guide incident response.
- **INCIDENTS** — The **INCIDENTS** are the incident records, postmortems, corrective actions, and learning events.
- **REGRESSION LEDGER** — The **REGRESSION LEDGER** is the durable catalog of failures that future releases must continue to pass.
- **NEXT.JS** — The **NEXT.JS** is the TypeScript/React application that receives user-facing requests and continues telemetry context on the server.
- **FASTAPI** — The **FASTAPI** is the Python backend service that processes requests, enforces policy, and emits durable business records.
- **MCP** — The **MCP** is the Model Context Protocol connection to tool capabilities and resources.
- **A2A** — The **A2A** is the agent-to-agent protocol used to delegate tasks, receive artifacts, and coordinate work.
- **RAG** — The **RAG** is the retrieval-augmented generation pipeline that finds, filters, and ranks evidence.
- **TOOLS** — The **TOOLS** are the external capabilities the agent can invoke with typed arguments and receipts.
- **QUEUES** — The **QUEUES** are the asynchronous work items that carry context across time and load shapes.
- **UI** — The **UI** is the user interface where progress, evidence, controls, and receipts are shown.
- **VERIFIED LEARNING** — The **VERIFIED LEARNING** is the teal loop that returns proven improvements back to the build stage.
- **BUILD** — The **BUILD** is the build stage that receives verified learning and produces the next candidate.
- **STALE ANSWER** — The **STALE ANSWER** is the coral catch at retrieval that blocks a release before it reaches users.
- **RETRIEVAL** — The **RETRIEVAL** is the stage where evidence is found, filtered, and ranked; it is where a STALE ANSWER is caught and blocked.
- **RELEASE** — The **RELEASE** is the gate or stage that must be blocked when a stale answer or other failure is caught.

## Colour and flow semantics

- **Cobalt platform** — a service, stage, dataset, quality gate, budget, release lane, or incident-control boundary. In this diagram it appears on **ACME AGENT QUALITY LAB**, **TELEMETRY CONTRACT**, **TRACE EXPLORER**, **EVAL DATASET**, **STAGE QUALITY**, **LATENCY COST CAPACITY**, **RELEASE GATES**, **SHADOW CANARY** and others.
- **Cyan arrow** — a request, propagated context, telemetry signal, evaluation flow, or candidate release path. In this diagram it appears on **FLAGS ROLLBACK**, **ALERTS RUNBOOKS**, **NEXT.JS**, **FASTAPI**, **MCP**, **A2A**, **RAG**, **TOOLS** and others.
- **Teal arrow** — a healthy result, matched evidence, safe promotion, controlled degradation, recovery, or verified learning path. In this diagram it appears on **VERIFIED LEARNING**.
- **Coral path** — a broken trace, failed assertion, regression, overload, unsafe outcome, rollback, alert, or incident path. In this diagram it appears on **STALE ANSWER**.
- **White card** — a span, event, metric, log, resource, case, score, budget, version, release, runbook, action, or regression record. In this diagram it appears on **SCORERS**, **INCIDENTS**.

The overall flow moves from the inputs on the left through the incidents and continuous learning stages and exits as either a teal healthy path or a coral failure path. White cards carry the records, cobalt platforms hold the boundaries, and the cyan arrows show propagation and requests.

## How to present it

- Start with the operational question the team actually needs to answer. Point at the central element and ask what a regulator, evaluator, or support operator would ask about this outcome, and which signal type would best answer it.
- Ask the room what the team would need to know before approving the next release. Point at **ACME AGENT QUALITY LAB** and **STAGE QUALITY** and ask what would change if this step were skipped? Use the case study to make the failure concrete.
- Have the group list the operational decisions this stage informs. Highlight the trace and ask what real decision does this evidence support? Use the case study to make the failure concrete.
- Ask what evidence would change the route a support ticket takes. Trace with your finger **SCORERS** and **UI** and ask what would a missing or corrupted value look like here? Use the case study to make the failure concrete.
- Get the room to name the owner who would need this evidence in an incident. Put a marker on **RELEASE** and ask who owns the evidence produced at this step? Use the case study to make the failure concrete.
- Ask what would need to be true for the team to skip this stage safely. Ask the room to locate **INCIDENTS** and ask which downstream stage would fail if this step were wrong? Use the case study to make the failure concrete.
- Use the analogy. It is an airport operations center: flight plans, radar, maintenance records, passenger outcomes, weather, capacity, safety checks, release approvals, incident teams, and lessons learned connect without becoming one giant ungoverned database. Ask the room where the equivalent tracking number, queue, or ledger is in their own system, and where it would first break.
- Tell the case study — Maya receives a plausible but obsolete refund policy answer. Walk through the walkthrough and stop at the moment the failure first becomes visible. Ask what signal, gate, or version field would have caught it earlier.
- Run the lab. Produce the full Quality Lab specification: component map, 30-field telemetry contract, ten evaluation cases, twelve stage assertions, six slices, latency and scenario-cost budgets, load profile, four release stages, compatibility matrix, three alerts, two runbooks, one exercise, one postmortem template, and a regression ledger. Label every unmeasured number proposed. Have each group label the fields that are captured, hashed, redacted, or omitted.
- Pose the checkpoint. Is the Acme Agent Quality Lab one dashboard or one observability vendor? Let the room answer before confirming with the answer. Then ask what the team would change in the next build based on the answer.
- Before moving on, ask the room to trace one healthy teal path and one coral path through the diagram, naming the evidence that flips the colour at each stage.
- Close on the contract. Connect user outcome to stage evidence, release decisions, recovery, and permanent learning. Make the group write one sentence that ties the lesson to their own system.
